	\section{Evaluation}
		This section evaluates the implementation status and its alignment with initial expectations. It details what has been implemented, to what extent, and assesses the quality and completeness of the implementation.
		
		Additionally, it reviews the features outlined in the MoSCoW analysis, evaluating the degree to which each has been implemented and whether it meets the intended requirements.
			
		\subsection{Requirements Evaluation} \label{sec:RecEval}
			\begin{itemize}
				\item \textbf{FR0 - Individual Process in each node:} This works as planned and expected. C\# tasks enable nodes to run in parallel as intended.
				\item \textbf{FR1 – Communication with Other Services:} Implemented using RabbitMQ, which successfully enables service-to-service communication. The only missing feature is queue prioritization, which was deferred in favour of higher-priority tasks. However, the system is designed to support priority implementation in the future. It is considered fulfilled with a few non essential features missing.
				\item \textbf{FR2 – Ease of Adding New Event Nodes:} New nodes can be added efficiently using the \gls{json} configuration system, allowing a new setup to be completed within minutes (see Code Snippets~\ref{lst:simpleAddition}, and~\ref{lst:BotCreation}). Event nodes containing simple models may occasionally raise exceptions due to syntax errors when writing C\# code directly in it, this can be further mitigated with additional development such as a \gls{dsl}. This requirement is considered fulfilled, with room for implementation improvements. However, the system does not currently support adding event nodes at runtime. While this feature could offer value for example, by preserving the current state of active nodes, it was deprioritised in favour of more critical functionality.
				\item \textbf{FR3 - Being able to quickly start up \gls{reps} using a config:} When excluding syntax errors, the system starts reliably using the configuration file. This functionality is considered stable and effective.
				\item \textbf{FR4 – Support for \gls{ml} Models in Event Nodes:} Successfully implemented with two \gls{ml} models: \gls{svm} and \gls{rf}. The current design allows each node to contain and manage its own model, making it straightforward to incorporate additional models in the future. The only potential limitation concerns models with high memory usage, such as \gls{knn}, which may impact performance.
				\item \textbf{FR5 – Event Detection Capability:} Successfully implemented. While the current implementation confirms that event detection is possible, further work is required to evaluate the accuracy and reliability of detection. The focus at this stage was on feasibility; assessing effectiveness will follow in future work.
				\item \textbf{FR6 – \gls{gui}:} Development was initiated but not completed. This requirement is not considered fulfilled.
				\item \textbf{FR7 – Automatic \gls{reps} Creation:} Not initiated and therefore not fulfilled.
			\end{itemize}

		\subsection{complexity}\label{sec:complexity}
			It was found that \gls{reps} exhibits low complexity. As complexity is an abstract concept in software, this report presents two arguments to support the claim:
				\begin{itemize}
					\item \textbf{Technological Complexity:} The \gls{reps} pattern requires minimal technological overhead. A communication platform similar to the MQTT standard and a data format such as JSON are sufficient to configure the system. Alternatively, a web interface or other \gls{gui} could replace manual configuration. As a result, the technical knowledge required to use the pattern is limited.
					\item \textbf{Configuration Overhead:} Defined as, knowledge a user need to attain to be able to fully configure \gls{reps}. The current implementation uses 30 unique keywords, keywords being predefined reserved identifiers which the \gls{reps} makes use of (Appendix~\ref{sec:Keywords}). There is three non-essential keywords introduced for optimisation or to manage technical debt in the current implementation. One way to assess usability is to implement a basic function similar to a “Hello World”. Since \gls{reps} is designed for decision-making rather than data generation, a simple addition example is provided (Code Snippet~\ref{lst:simpleAddition}, page 22).

					For a more detailed example, a basic service has been developed to detect the mass creation of bot accounts on a website (Figure~\ref{fig:BotCreation}).

				\end{center}
			\end{itemize}
			
			\subsection{Measurements}\label{sec:measurements}
				This section discusses CPU and memory usage, presenting observations relevant to likely scenarios where \gls{reps} may be deployed. Latency is excluded, latency being the average time from event actually starts to REPS makes a determination. Latency depends largely on the update rate of \gls{reps} and network transport times. Program size is also not considered critical due to varying edge cases in different environments; for reference, the latest Debian Docker image occupies 231.81 MB.
				
				\subsubsection{CPU Usage}
					Each node uses very little processing power. Usage varies depending on the model, but the current implementations are so lightweight that a reliable assessment cannot be constructed. Nodes run in parallel, utilising all available CPU threads. When the number of nodes exceeds the number of CPU cores, \gls{reps} will use 100\% of the CPU by processing multiple nodes concurrently, scheduling tasks as resources become available.
					
					This can be problematic, as it may not be desirable to utilise all available resources unnecessarily. Therefore, some form of resource limitation should be considered in future work to prevent excessive hardware usage.
					
					The current implementation writes extensively to the console to actively monitor the system’s state. Approximately 52\% of CPU usage is attributed to logging. While retaining some logging may prove useful for future debugging, it appears to consume a significant proportion of resources and may not be justified under normal operation.
					
					CPU usage is minimal and therefore not a primary concern for further analysis.
					
				\subsubsection{Memory Usage}
					The simple bot detection service (see Figure \ref{fig:BotCreation}) consumes between 65 and 70 MB of memory, of which 25.85 MB accounts for overhead, including communication with RabbitMQ, logging, and related processes. Running the same service without the simple model (a run-time compiled method) reduces memory usage to between 41 MB and 44 MB. Adding an additional simple node to the original service increases memory consumption to approximately 75 MB, indicating an overhead of around 10 MB.  The \gls{svm} model uses approximately 4 MB with five features. The memory usage of the timed model is negligible.
					
					Memory usage is a important metric to design around based on these readings.

	\section{Discussion}	
	
	\subsection{Simulator}
		The Simulator worked great for testing and generating data to train models on. There were a few problems from iteration to iteration where the site which the test was run on would change and therefore the Simulator would have to change as well.
		
	\subsection{Hindsight}
	In this section, a overview of the good tactics and the tactics which a developer should avoid when making \gls{reps} or similar systems.
	
	\subsubsection{Good tactics}
		Setting up a proper development environment for this project is crucial, developing for docker in mind allowed for separation from the developers environment and test \gls{reps} more efficiently. The thread count for this program has lead to unforeseen problems and deploying on docker lowered the risk of my system having any affect on the test. Deploying on docker also allowed me greater deal of control of memory and version control.
		
		For this project, it was planned more than the developer would usually do for a project, and yet tech-debt is a larger problem than expected. This is attributed to two things, the C\# Roslyn library, as requirements changed throughout this project, the method to compile the user specified function needed many changes and test to verify the behaviour.
		
		Making a \gls{json} interpreter for this project has boosted development speed and most likely has overcome the initial time-cost which it cost to make it.
		
		Using MQTT fits very well with \gls{reps} and has not caused any problems.
	
	\subsubsection{Tactics to avoid}
		There was a focus on getting a \gls{mvp} ready to test and discover any problems with the project idea, design or other. This seems to be a mistake as it has created a lot of tech-debt which slows down development of new features. This case did not meet any large change based on the first \gls{mvp}, spending more time to avoid tech-debt before achieving a runnable product would in this case better for the project.
	
		A logging tool was used which were developed in previous projects to help debugging. This tools was not developed to avoid race conditions which just caused more exceptions than it logged.
	
	\subsubsection{Other findings}
		I discovered that compiling an event node function in run time requires more resources as well as taken a large time to implement. While using a \gls{ml} model has more use cases and is often times depending on the model, cheaper in memory usage.
	
	\subsection{\gls{gui}}
		A \gls{gui} is useful for an end consumer, but working in this project it was not worth developing. The idea for developing it for this project even tough it already was a low priority, was to speed up the development process for the rest of the project. It could increase understanding if a visual was developed for the nodes in the \gls{reps} and allow me to more quickly create new config files to test. It turned out after one iteration of work that this would require too much time to finish to a useful state.
	
	\subsection{Reflection}
		This project changed a lot from the start of the project, while I generally think the project was a success, there is so much more that could have been done. I'm disappointed that I did not manage to make comparisons with other industrial technologies, nor did I manage to make more scenarios which could be used in the \gls{reps}. At the start I was unsure whether I would model \gls{reps} configs based on real data sets or virtual copy (find det rigtige ord), using the virtual copy was very good for the first experiment. It revealed a lot of the advantages for this project, and I did believe that the product wouldn't be worth developing until I started seeing the first result of the experiment.
		
		I would wish that I planned more time for experimentation, while the features generally kept up with the plan in terms of developing the product, when I started to experiment there would be a lot of small changes that would be needed and was only really revealed once experimentations started. It was for example at this point I noticed the value of having a timer node, which is more of a support node than a event node.
		
		Simple models took too long to implement, they are memory heavy, they are useful in some scenarios but the \gls{ml} models were useful in more scenarios, were better, and lighter on the memory. I now know that this should have been a could have on the MoSCoW analysis and should properly first have started developing on after experiments. 
		
		If I were to redo this project, I would not develop simple nodes at least until the first set of experiments were finished, I would further increase the amount of time spent on experimentation. It is clear now that the extra time was needed for the experimentation. So I at least could gather more data because at the current value of this project is more of if it possible to do rather than to what degree is it useful. While I made a few determinations on this project, they are abstract to some degree and is not based on direct data but rather my experience on this project.

	\section{Conclusion}
		I developed \gls{reps}, a pattern to make determinations where units(find bedre ord) of data have a relation to one another. By combining \gls{mqtt}, \gls{json} and parallel node interpretation \gls{reps} was created. I managed to determine a good way to develop \gls{reps} and learn what works and what does not, thereby allowing future developers to develop similar system without going trough the same pitfalls and take inspiration from what worked in this project. \gls{reps} manages to make determinations while keeping complexity low, allowing a user to easily design their system in few precise keywords. This project proves that \gls{reps} is a viable solution to make determinations, next step is to determine how useful it is compared to other industrial solutions. \gls{reps} might lead to a more developer friendly determiner that isn't beholden to individual solutions but rather can combine models based on their usecase.

	\subsection{Number of keywords}\label{sec:Keywords}
	This is a list of all of the keywords which \gls{reps} uses
	\begin{enumerate}
		\item BrokerInfo : An object containing required info for the broker
		\begin{enumerate}
			\item NotificationBroker : Where \gls{reps} should notify the user on an event
			\item NotificationTopic : What topic it should notify
			\item ReportBroker : Where it should report to
		\end{enumerate}
		\item SensorNodes : An object containing all sensor nodes
		\begin{enumerate}
			\item ID : used to refer back to it
			\item Name : Used to make error handling easier
			\item Host
			\item RoutingKey
			\item Topic : What topic to report to
		\end{enumerate}
		\item EventNodes : An object containing all event nodes
		\begin{enumerate}
			\item ID
			\item Name
			\item SensorNodes : An array of id for all sensor nodes which this node should retrieve data from
			\item EventNodes : An array of id for all event nodes which this node should retrieve data from
			\item ReportTopic
			\item SupportedType : Determination of what type the node should work as, this keyword can in theory be removed but exists still due to tech debt.
			\item Host
			\item RoutingKey
			\item Model : An object containing all information for the model
			\begin{enumerate}
				\item ID
				\item Type : What model type it is, this follows with their own keywords
				\item isUsername : if you handle usernames or other similar text based input, you can use this. This is not needed for the pattern or a user, but I found it useful for optimisation purposes.
				\item DebugMode : puts the model into debug mode
				\begin{enumerate}
					\item simpel : A model which the user can define themself with code
					\begin{itemize}
						\item Function : A function in C\# which will be compiled in runtime so the user can define themself.
						\item TriggerFunction : A logical function to determine when a event is triggered and should
					\end{itemize}
					\item timed : A model to find a average amount of unique
					\begin{itemize}
						\item TimedTrigger : A value limit to determine whether a event has happend or not
					\end{itemize}
					\item Adaptiv : A model that can change its trigger limit depending on its usecase
					\begin{itemize}
						\item QuantileCutoff
						\item UpdatePercentage
						\item It also shares it the same keywords as simpel
					\end{itemize}
					\item svm : Support Vector Machine model
					\begin{itemize}
						\item TrainingData : Path to the trainingsdata
					\end{itemize}
					\item forest : Random Forest Modell
					\begin{itemize}
						\item TrainingData
						\item NumberOfTrees
					\end{itemize}
				\end{enumerate}
			\end{enumerate}
		\end{enumerate}
	\end{enumerate}
